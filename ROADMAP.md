# CHIMERA — Roadmap

**Status:** Initial planning baseline; not blanket implementation authorization.  
**Repository:** https://github.com/GenX-Shinobi/CHIMERA

## Mission
Build a free-to-use, open-source, platform-independent framework for creating, governing, coordinating and improving reusable AI workforces.

## Guiding principles
- Establish governance and memory foundations before building a large workforce.
- Preserve human ownership and explicit approval for material changes.
- Keep provider-specific integrations optional; do not make one platform a core dependency.
- Add roles only when demonstrated value exceeds coordination, context, compute and maintenance overhead.
- Separate CHIMERA-wide knowledge from project-specific knowledge, authority and data.
- Use evidence and bounded pilots rather than speculative complexity.

## Progression

### Phase 0 — Governance foundation (current)
- [x] Create a separate public repository.
- [ ] Decide whether project commitments are Foundational or Controlled.
- [ ] Define statute hierarchy, conflict handling and amendment procedure.
- [ ] Define project/employee separation and portability boundaries.

### Phase 1 — MEMORY first
- [ ] Finalize the four-level model: Working, Episodic, Semantic and Procedural.
- [ ] Define shared organizational memory and individual employee working memory.
- [ ] Define role-based access, provenance, approval status and version history.
- [ ] Define safe handoffs, retrieval, updates, recovery and employee/platform replacement.
- [ ] Build a small proof of concept before broad employee development.

### Phase 2 — CHIMERA Administrator
- [ ] Define the Administrator charter, permissions, limits and review process.
- [ ] Begin with ChatGPT as the initial Administrator while keeping the role replaceable.
- [ ] Ensure the Administrator is subject to the same universal statutes as every employee.
- [ ] Validate coordination without self-authorizing changes or granting permissions.

### Phase 3 — Reusable employee framework
- [ ] Define employee identity, charter, scope, capabilities, permissions and memory boundaries.
- [ ] Define recruitment, evaluation, time-limited pilots and owner approval.
- [ ] Define delegation, reporting, review, correction and escalation.
- [ ] Define controlled learning and employee-instruction versioning.
- [ ] Evaluate optional adapters (including Claude Skills and webhooks) only after portability and free-use implications are assessed.

### Phase 4 — Pilot and validate
- [ ] Test continuity across sessions and, where feasible, different AI platforms.
- [ ] Test authorized retrieval, provenance, access boundaries and recovery.
- [ ] Test bounded delegation and explicit deliverable/completion criteria.
- [ ] Test statute compliance and conflict escalation.
- [ ] Record failures and revise only through approved governance.

### Phase 5 — First adopter: AI Prompt Builder Hub
- [ ] Do not integrate CHIMERA until Prompt Builder v5.4.0 is formally completed and owner-approved.
- [ ] Reassess integration against Prompt Builder's live roadmap and project-specific rules.
- [ ] Pilot a small, bounded assignment before wider adoption.
- [ ] Keep repositories, roadmaps, statutes, memory and release decisions separate.

### Phase 6 — Sustainable evolution
- [ ] Establish contribution, maintenance, compatibility and release procedures.
- [ ] Evaluate new roles and capabilities using demonstrated need and overhead.
- [ ] Publish portable templates and examples usable without paid AI subscriptions where practical.
- [ ] Maintain an auditable history of approved changes.

## Authorization boundaries
This roadmap is a planning document, not permission to implement every phase. The owner authorizes milestones and material changes. Within an approved milestone, routine work may proceed under bounded autonomy. Statute changes, authority changes, permanent appointments, major architecture/dependency changes, scope changes and publication/release actions require explicit owner approval.
